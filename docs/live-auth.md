# Live authentication and private handoff

Open [Connections](http://127.0.0.1:4173/) after `npm run dev`. GitHub, Stripe and Supabase share this entry point and private session environment. There is no separate live connection screen. Tests exercise the actual SDKs with synthetic provider responses; this is not certification against credentialed live accounts, Cloudflare, an A2H gateway or an end-user MCP host.

## Stripe and Supabase execution

`serviceRegistrations(db, environment, options?)` is exported from `@ceremony/auth/server`. Spread its registrations into the same durable `CeremonyController` as GitHub. `serviceManifests` and `serviceWorkflows` are exported for host composition. The optional trusted-host `fetch` and `onStep` bindings support contract testing and secret-free workflow observations, never model-provided endpoints or code. The same React component, framework-neutral client, WebMCP actions and private collectors drive all registrations.

- **Stripe:** Connect starts the registered `stripe.prepare-account` → `stripe.obtain-key` → `stripe.verify-access` recipe in the async runtime. Missing account setup opens an isolated native page with Stripe-owned signup/sign-in links. Account readiness is an authenticated user's setup choice, not proof of account ownership. It leads directly to restricted-key collection. `STRIPE_SECRET_KEY` in the shared session skips those human setup steps; it never skips verification. The official `stripe` SDK calls `balance.retrieve()` through the existing Arazzo binding, requiring Balance read permission and matching test/live mode. Rejected keys have a private replacement path. Completed access is reverified when reused, not when reading a snapshot. Only encrypted server-owned artifacts carry credentials; recipes and agent tools contain none. No payments, charges, accounts, or API keys are created by the server. Provider signup, email verification, MFA, and key issuance remain provider-owned human actions.
- **Supabase:** Connect now uses `supabase.prepare-project` → `supabase.obtain-session` → `supabase.verify-access`. Missing project configuration opens isolated native guidance for Supabase dashboard signup/sign-in and project setup, followed by project URL/publishable-key collection. Shared-session `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` (or legacy `SUPABASE_ANON_KEY`) skip that configuration form. Project-user sign-in or explicit signup follows; it is not dashboard authentication. The official SDK executes signup, confirmation recovery, sign-in, fresh `getUser` verification and enrolled TOTP challenge/verification through Arazzo. A configured host can require `aal2` with `supabase.requiredAssurance`; otherwise it requires `aal1`. Missing/unsupported factors remain blocked, not authenticated. The private page allows fresh input after rejection or uncertain results and returns to the same parent. A signup attempt is never automatically repeated after a lost response.

The Supabase children accept hosted `https://<project>.supabase.co` origins and publishable/legacy anon keys only; secret/service-role keys, custom origins and self-hosted deployments are rejected. Project configuration does not prove dashboard ownership. Passwords awaiting signup confirmation remain encrypted for at most 15 minutes, without extending retention on checks; they are deleted once a session is obtained. Collected TOTP codes expire locally after five minutes and are consumed before the external effect, never automatically replayed. Session tokens remain encrypted and are freshly verified before reuse. SDK persistence and background refresh are disabled. TOTP enrollment, phone/WebAuthn factors and CAPTCHA continuations are not implemented; they must not be represented as successful authentication. The legacy `serviceRegistrations` Supabase form remains existing-user-only and does not retain passwords; it is not the account-first Connect path.

Both use trusted SDK operation bindings executed by the bounded Arazzo runner, with no implicit workflow retries. Supabase's OpenAPI document does not define an operation ID for `/token`, so its workflow uses Arazzo's `operationPath`. Completed connections resume for the same owner until their recorded expiry. Account/project creation and API-key issuance are not silently performed; an authorized owner obtains those on the provider's site when necessary.

Official boundaries: [Stripe balance read](https://docs.stripe.com/api/balance), [Supabase password sign-in](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [Supabase client options](https://supabase.com/docs/reference/javascript/initializing).

Stripe's account and key guidance follows [Stripe account setup](https://docs.stripe.com/get-started/account) and [API keys](https://docs.stripe.com/keys). The same Stripe children are available from `@ceremony/auth/server/teaching` for reviewed whole/partial recipes. Local HTTP and browser fixtures exercise the actual SDK, protected commands, database, collector, and return path; they do not certify a real Stripe account or automate provider-required human checks. Supabase's account/project-registration prerequisite path and the remaining connector families are still being completed; its legacy sign-in adapter is not a substitute for that end-to-end path.

## GitHub execution

One fixed recipe composes three blocking prerequisites: prepare a GitHub App, authorize its installation, then verify access. Existing owner-scoped app configuration is reused. Otherwise the trusted broker posts a [GitHub App manifest](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) for the owner to approve. The callback converts its one-use code on the server and verifies the app with a signed JWT. Installation approval is followed by server-side app/account checks, a read-only installation token, and a repository API request. Only verified provider evidence produces a connection reference.

OAuth Apps, device clients and GitHub Apps are different configurations. This recipe does not register an OAuth App. Account login, MFA, CAPTCHA and consent remain human-owned. A crash during a one-shot conversion enters recovery; it never blindly creates another app. The owner can privately provide the existing app ID and PEM key for signed verification. Cancel/expiry fences stale callbacks but does not delete an app or revoke previously issued provider credentials.

The GitHub adapter projects ordinary `AdapterUpdate` fields and prerequisite status into the existing headless client. React renders a scoped, accessible ordered summary. External hosts can replace that renderer, use their UI library and style tokens, or use the same client directly in Vue. There is no second workflow engine or framework transpiler.

```ts
import {
  CeremonyDatabase,
  PrivateCredentialBroker,
  CeremonyController,
  GitHubAppCeremonies,
  githubAppManifest,
} from "@ceremony/auth/server";

// All arguments below come from host configuration, never tool arguments.
const db = new CeremonyDatabase(databasePath, vaultKey); // 32-byte key
const github = new GitHubAppCeremonies(db, {
  origin: publicOrigin,
  // Optional shared app: { id, slug, pem, owner: { login } }.
  // A shared app also requires expectedAccount: the authorized installation account.
});
const controller = new CeremonyController(
  [
    {
      manifest: githubAppManifest,
      recoverable: true,
      createAdapter: (context) => github.createAdapter(context),
      resume: (owner) => github.resume(owner),
    },
  ],
  new Map(),
  Date.now,
  { database: db, broker: new PrivateCredentialBroker(db) },
);
```

Derive every `owner` from authenticated host identity. Mount start/read/action/collection and fixed callback routes; `examples/server.ts` is the reference. For trusted cross-device callbacks, `github.callbackOwner` validates the one-use provider state before choosing the owner. Never let a caller choose their owner, app identity or arbitrary redirect URL.

## Storage and configuration

### Environment section

Open [Environment](http://127.0.0.1:4173/?mode=live&section=environment). Optionally import a `.env` file or save a named value. All connectors share this session environment by default. Import merges assignments and replaces matching names; Remove deletes the selected session variable. Values are masked during manual entry and are never returned by the metadata endpoint. To edit a saved value, enter its name and replacement. An empty value is allowed; removal is explicit.

The server uses Node's `.env` parser, including quoted multiline values, with no shell execution or variable expansion. Limits are 100 variables, 64 KB total, and 16 KB per value. Names must match `[A-Za-z_][A-Za-z0-9_]*`. Invalid edits and stale revisions are rejected. The file is not written to disk; parsed variables go into encrypted storage scoped by session owner. Losing the owner session loses UI access to that environment. The demo does not expose or modify `process.env`, vault keys, service origins or server credentials. Legacy connector records are merged once without deleting originals; conflicting duplicate values block migration instead of silently overwriting a secret.

GitHub consumes `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_OWNER`, and `GITHUB_APP_PRIVATE_KEY` together when setup begins. An incomplete set blocks setup with an actionable message; no set uses guided registration. Provider signature/identity/permission checks still apply. Already configured attempts retain their pinned app; changing Environment does not silently switch an in-progress authorization. Stripe and Supabase consume the shared variables described above. Developer simulations do not consume real credentials.

External adapters use `CeremonyEnvironment.read(owner)` on the server. `describe(owner)` returns names/revision only; `update(owner, edit)` performs session-scoped encrypted edits with optimistic revisions. `/api/environment` is the canonical endpoint; legacy connector URLs alias the same session environment. `GitHubOptions.resolveApp(owner)` supplies configuration when the ceremony starts. Environment editing is private configuration, not a model tool accepting raw secrets; WebMCP ceremony actions and hooks never receive the uploaded values. Hosts must exclude this native input page from DOM capture, session recording and analytics, just like private credential collectors.

GitHub starts directly at its first unmet prerequisite. Without a session app, the provider handoff automatically posts the registration manifest. With an available app, registration is skipped. The registration callback continues directly to GitHub installation approval, followed by server-side signature, identity and repository-access verification. No intermediate local setup/review button is required; GitHub's own approval remains human-controlled.

Local CLI startup creates `.ceremony/vault.key` (0600) and encrypted `.ceremony/state.sqlite` in a protected directory. Keep this directory private. The development file server denies vault/key/database downloads. For deployment, put the key outside the database and backups, preferably in a secret manager; encryption at rest is not protection from a compromised server.

- `CEREMONY_DATABASE` and `CEREMONY_VAULT_KEY` must be supplied together; the latter is a 64-character hexadecimal encoding of a 32-byte key.
- `CEREMONY_ORIGIN` selects the exact callback origin. Remote browsers require publicly reachable HTTPS.
- The loopback reference app uses anonymous owner cookies, not a production account system. Host authentication and a recipient-to-owner mapping are required for cross-device human links.
- Only adapters marked recoverable may use durable controller storage. Existing simulation adapters are intentionally not marked recoverable.
- Run one active controller process. SQLite leases reject overlapping actions, but lease expiry is not a distributed fencing protocol. Add operational retention and connection lifecycle management before production; expired encrypted records are not automatically purged.

## Private input and MCP Apps

WebMCP `request-input` opens an isolated native collector. Credentials travel directly to the broker; `/actions` accepts the resulting one-use reference. References expire after five minutes and are bound to owner, instance and revision. There is no model-facing secret resolution tool. Encoding alone is not used as a privacy mechanism.

`registerPrivateCollector` from `@ceremony/auth/server` registers official MCP Apps resources/tools on a host-authenticated MCP server. Supply `{ brokerOrigin, appOrigin, appHtml, owner(context), requestOwner(request) }`. Both identity adapters must derive the same tenant-aware opaque owner from authenticated host sessions; never return an unsigned request owner/header. `requestOwner` returns `null` when HTTP authentication is absent. Bundle `mountPrivateCollector(root, brokerOrigin)` from `@ceremony/auth/mcp-app` into trusted `appHtml`; do not use generated HTML. Mount the returned `handleRequest` at `https://<broker>/ceremony/private-collection`.

The tool sends only a collection grant in app-only metadata. The iframe posts native values directly over HTTPS with credentials restricted to the exact trusted broker endpoint, clears the form, and calls the binding tool with the reference. The broker accepts only the configured app origin, requires the independently authenticated recipient to match the grant owner, rejects opaque/null origins, and consumes each grant once. It enables credentialed CORS only for that exact app origin. A handle alone does not authorize collection. If browser cookie policy prevents the broker session from being sent, continue in the authenticated ceremony webpage; never copy session tokens into model-visible tool arguments. Unsupported MCP hosts fail closed and direct the human back to that webpage. The library does not install or configure a third-party MCP host.

Migration: the `requestOwner` option remains optional in the TypeScript shape for source compatibility, but omitting it now disables collection. Existing integrations must add authenticated HTTP recipient resolution and permit their secure broker session in the intended app context. Missing, invalid, expired, wrong-recipient or replayed grants fail closed. This hardening does not migrate the legacy synchronous controller/broker to the async teaching runtime: legacy consume-once references still lack durable command recovery. Production teaching MCP remains disabled/uncertified until a separately tested async bridge is provided.

The SDK transport test checks a sentinel against every JSON-RPC message. This does not certify host telemetry: before enabling a host, verify that its screenshots, accessibility/DOM capture, logs, recordings and analytics cannot observe private fields. Never enable model browser capture on a private collector or provider login screen.

## Connector OAuth for imported descriptions

An imported OpenAPI description, once a reviewer approves it into a runtime binding, can now obtain its own credential through the connector command service instead of refusing with `adapter.authorize-unsupported`. What happens is decided by the bound authentication profile and by host policy, never by the document:

- **OAuth authorization code (PKCE S256) and OpenID Connect:** `connect` returns a provider-browser handoff; the provider redirects to the fixed `/api/v1/connectors/callback` route, which completes it for the person who started it. The grant settles its own handoff under the connection's generation fence (`CompletionResult.handoffSettled`).
- **OAuth device authorization:** `connect` shows the user code and verification URL; `poll` completes it, keeping the issuer's `slow_down` interval between polls. When a browser login reaches the provider's verification page instead, the agent types the user code only if its plan was given one as the `user-code` role; otherwise the person is handed the verification URI (origin and path, never the `verification_uri_complete` query) to enter the code themselves. The device code is never typed anywhere. See [handoffs](browser-login-sessions.md#handoffs); this is fixture evidence against the auth double's verification pages, not a certified provider.
- **OAuth client credentials:** no person takes part; the grant runs when `connect` verifies the connection, for a confidential client only.
- **API key, HTTP Basic, HTTP bearer:** `connect` opens an input-required handoff; the initiating person submits the values to `POST /api/v1/connectors/connections/:ref/handoffs/:handoff/input`. They go to credential custody and nowhere else, and are checked against the destination only when the binding names a verifier operation.

Every OAuth profile needs a host-written issuer policy pinned in the binding's settings — `settings.oauth`, or per profile under `settings["oauth-profiles"][profileId]` — naming the issuer, how the client exists there (pre-registered configuration names, CIMD or dynamic registration in order) and which origins may be contacted. A reviewer supplies these in the binding approval itself, in `POST /api/v1/connectors/bindings`: the binding-wide policy as `approvals.oauth` (stored as `settings.oauth`) and per-profile policies as `approvals.oauthProfiles` (stored under `settings["oauth-profiles"]`). Only a human reviewer may set either (`oauth.policy.human-only`); each must parse as an issuer policy (`oauth.policy.invalid`); and the host's `allowIssuer` policy must admit its issuer and origins (`oauth.issuer.not-permitted`). `oauth` and `oauth-profiles` are reserved in `approvals.settings` (`settings.reserved`), so neither can arrive as an inert setting. The authorization and token URLs a description declares are hints for the reviewer to copy into that policy; they are never called on their own. Without a policy the answer is `openapi.oauth-policy-missing`; a missing client id or secret surfaces as `configuration-required` with the configuration names.

On invocation, a token custody reports as expired, or one the destination refuses with 401, is renewed once — a refresh-token grant, or a fresh client-credentials grant — under custody's single-flight lock, and the call is retried once; the retry is its own effect-journal entry, and the refused attempt is recorded as not applied. A refusal that renewal cannot cure is returned as it came, without a loop. Tokens never appear in invocation results, connection records, handoff summaries or the effect journal.

The remote MCP adapter uses the same authorization-code grant as its default OAuth profile when the binding carries `settings.oauth` and the server's protected-resource metadata names that issuer; the token is bound to the server's canonical resource (RFC 8707). A deployment passes the optional host seams — a store for dynamic client registrations, the metadata cache, a CIMD publisher — through `ConnectorInventoryOptions.oauth`.

This is protocol-fixture evidence against the loopback authorization server double and a fixture API; it is not certified against any provider. JWT assertion grants are not implemented. Remote MCP connections under the default profile renew their token once, single-flight, on invocation, on verification (which reconnect and polling reach, as does `connector_verify`) and on the continuation of a suspended input request; on verification only a renewal the issuer refuses leaves the connection needing a person (`reconnect-required`, `mcp.credential-renewal-failed`). An issuer that cannot be reached leaves it as it was, answering `pending` with `mcp.credential-renewal-unavailable` so it can be verified again later, and a refresh that was cancelled, raced another worker or lost its response is `indeterminate` (`mcp.credential-renewal-indeterminate`); a refresh token that may have been spent is never presented again. An invocation, or a person's answer to a suspended input request, classifies its renewal the same way: a refusal answers `denied` with `mcp.credential-renewal-failed`, an unreachable issuer `failed` with `mcp.credential-renewal-unavailable` (retry later), and an unknown outcome `indeterminate` with `mcp.credential-renewal-indeterminate`. In each case the operation never ran, and the adapter's journal keeps that attempt `not-applied`, so a later attempt may still run it. None of these carries an issuer message. Upstream revocation on disconnect runs only where the reviewed issuer policy asks for it.

## Account sign-ins: AWS IAM Identity Center and Vercel

These two adapters are the device-code experience of `aws sso login --use-device-code` (since AWS CLI 2.22.0 the CLI's default is authorization code with PKCE) and of `vercel login`. The person signs in and approves on the provider's own page, the host holds the resulting credential, and the caller is only ever given an opaque connection reference, what the connection is for (an account and role, or a team) and when the credential lapses. Both run the same device-code handoff as the OAuth device row above, so a person sees one link and one code and nothing else; neither is certified against its provider. The evidence is `protocol-fixture` against loopback doubles (`tests/connectors/doubles/aws-identity-center.ts`, `tests/connectors/doubles/vercel-account.ts`) that each import nothing from the adapter they check.

**What a binding names.** Both are `hosted-server` adapters for a `user` owner (an organization or workload owner is refused before anything is sent). A reviewer approves a binding with an `oauth-device` profile and the settings below; a binding that permits no account (AWS) or no team (Vercel) is refused before anyone signs in.

|                   | AWS IAM Identity Center (`aws-identity-center`)                                                                                                                     | Vercel account (`vercel-account`)                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Settings key      | `aws-identity-center`: `region`, `startUrl` (HTTPS), `clientName`, `scopes`, `requestTimeoutMs`                                                                     | `vercel-account`: `scopes` (default `openid offline_access`), `requestTimeoutMs`; the issuer policy is `settings.oauth` (`vercelAccountIssuerPolicy()`)                                                                                                                              |
| Destinations      | `oidc` and `portal`; a public destination must be exactly `oidc.<region>.amazonaws.com` and `portal.sso.<region>.amazonaws.com` for the reviewed Region, over HTTPS | `api`; a public destination must be exactly `https://api.vercel.com` with no path prefix; the issuer `https://vercel.com` and its endpoints on `api.vercel.com` come from the issuer policy, which trusts that one extra origin and refuses any other the issuer's metadata declares |
| Client            | One public client is registered per sign-in (`RegisterClient`); its secret lives only in custody and is released with the sign-in                                   | Pre-registered: an application made on the Sign in with Vercel dashboard page with client authentication `none`; its id is the configuration `VERCEL_ACCOUNT_CLIENT_ID`                                                                                                              |
| Permitted targets | `aws-account` ids (required), and optionally `aws-role` ids written `<accountId>:<roleName>`                                                                        | `vercel-team` ids (required)                                                                                                                                                                                                                                                         |
| Bound operations  | `awsIdentityCenterBoundOperations()`: list accounts, list the roles of a permitted account                                                                          | `vercelAccountBoundOperations()`: read the user, list the permitted teams                                                                                                                                                                                                            |

A public AWS destination must be the standard `oidc.<region>.amazonaws.com` and `portal.sso.<region>.amazonaws.com` hosts; the FIPS and dual-stack (`*.api.aws`) endpoints AWS also publishes are refused rather than guessed at, and a host that needs one has to widen the check deliberately.

**The choice after approval.** Approving at the provider signs the person in to everything they hold; a connection is for one thing. The adapter lists what the person holds, keeps only what the binding permits (and what the caller's intent named, if it named a target), and binds without asking when exactly one account and role (AWS) or one team (Vercel) is left. Otherwise the person types a choice, and nothing typed is believed: the provider's own list must contain it (`ListAccountRoles` for a role, `GET /v2/teams` for a team) and so must the binding. A choice that fails either check is refused, the choice stays open, and a valid one then works. Listings are read as sets, five pages of 100 at most; a listing that was cut off is unknown, not complete, so "exactly one" and "nothing permitted" are never concluded from it (AWS asks the person and checks what they type against the portal; Vercel asks too, answers `selection.listing-incomplete` when none of the teams read is permitted, and verifies a team it cannot find in a cut-off listing as `indeterminate`, not as left). A Vercel team beyond the page bound still cannot be picked, because a typed team is checked against the same listing. An agent actor can read the connection but cannot make the choice. The choice is claimed by one submission before any adapter runs (a compare-and-set on the handoff, shared by every connector that asks a person for input): a second submission with a different value, while the first is still being worked, is refused as `conflict` / `handoff.already-claimed` and changes nothing, so the connection is never labelled with a role whose credentials another submission fetched; the same value sent twice at once is answered from the first run (the second waits for it and returns the connection as it left it); a rejected attempt gives the claim back, and a claim left by a worker that died ends with its lease (twice the call timeout). The claim belongs to one attempt, named by a random token that is presented when the attempt settles or gives the claim back, so a worker whose lease lapsed cannot settle or release the claim of the submission that took over. What a claim holds of the values is a SHA-256 digest bound to the handoff and its generation, kept only inside the sealed record and removed when the handoff settles or is cancelled or the attempt gives the claim back (one left by a dead worker stays until the next claim replaces it or the handoff settles); it cannot be read back, but a low-entropy value (a short code) could be guessed against it, offline, by someone who can already read the sealed record while the claim is held, and no secret kept outside the store exists here to key it with. A same-value submission that joined another's run is answered only once that run has written the connection (it polls every 25 ms, for at most the lease, and stops when its own request is aborted). Redirects and provider events are not claimed, because their effect-journal entry already admits one.

While the choice is open the sign-in is held in custody under a reference the adapter records in the connection's own state (`pendingSession`, set when the choice is asked for and cleared when it is made) rather than in the handoff, whose private half only the person who signed in can read. Every actor therefore finds it: a disconnect (by a person, or by an agent, who may disconnect locally) and an administrator's revoke end that sign-in too, and a reconnect that is waiting on a choice has two (the one it replaces and the new one) and ends both. Cancelling the choice drops the waiting sign-in from custody without telling the provider (the drop every abandoned sign-in gets; a disconnect is what tells the provider), leaving a reconnect's own sign-in alone, and a new sign-in that reaches its own choice drops the one an earlier choice held. A choice that expires with nobody answering it leaves its sign-in in custody until a disconnect, a new sign-in or the record's own expiry, whichever comes first.

**What is held, and where.** One custody record per connection, behind the connection's single credential reference, so a local disconnect releases all of it. AWS keeps the client registration, the IAM Identity Center tokens and the role credentials together; Vercel keeps the access token and its refresh token. The account id, role name or team, and the user id are in the connection's state, which holds no credential. No tool, claim, event, journal entry or error carries a token, a role credential or the person's email address (`custody.test.ts` sweeps every surface for the exact values the doubles issued, with a positive control that finds them in custody).

**Renewal.**

- AWS role credentials last one to twelve hours. Renewing them is a new `GetRoleCredentials` call with the held access token, made inside custody's single-flight refresh when fewer than five minutes remain; only a lapsed access token costs a refresh grant, which is journaled before it is sent and presented once. A refresh whose portal call then fails (throttling, a timeout) still keeps what the refresh returned, because the token it spent is gone. A refresh token the journal already holds, or that an answer does not replace, ends the session as `expired` (`session.refresh-unknown` or `session.expired`), as Vercel's does. Trusted host code that must sign a request reaches the credentials through `withRoleCredentials`, which renews first and whose callback may not return them (custody refuses a result that contains one). The record holds no bookkeeping words: a sign-in's phase is read from which members it has, so an account or role may be named anything.
- Vercel's access token lasts an hour and its refresh token is single use and rotated. A token with under two minutes left is refreshed once, single-flight; a refresh that may have been spent (a 5xx or a lost answer) is never presented again, so the session ends and the person signs in again. A refresh Vercel refuses (`invalid_grant`, or `access_denied` for an application restricted to a team the person left), a person who removes the app in their dashboard, and a user without a refresh token all end the session the same way.
- Reconnecting is a new sign-in. A different team or role is refused without an explicit account switch (`verification.account-changed`), and so is a different Vercel user approving into the same team (`vercel-account.user.changed`, unless the intent asked for the switch).

**Bounds.** AWS calls and the Vercel REST reads (`GET /v2/user`, `GET /v2/teams`) read at most 1 MiB of response and time out after 15 seconds by default. Every request the shared OAuth client makes (device authorization, token, revocation, introspection, registration, pushed authorization, and the key set a token exchange verifies with) times out after 10 seconds and has its response read under a 1 MiB ceiling before the protocol library sees a byte of it. A response over the ceiling is refused as `upstream-rejected` with the detail `oauth.response.too-large`, an error that names the ceiling and carries none of the body: a declared `Content-Length` over it is refused without reading anything, and a stream that declares none, or less than it sends, is cut off where it crosses the ceiling, not after it has been read to its end. An answer over the ceiling to a request that spends something is unknown, not refused: the request was sent, so a device code or an authorization code may be spent, a single-use refresh token may have rotated and a token may have been minted. A device poll, a code exchange, a refresh, a client-credentials grant, a dynamic client registration, an RFC 8693 token exchange and the AWS OIDC refresh therefore end as `indeterminate` (everywhere the attempt is journaled it is journaled `indeterminate`, the same entry a lost answer gets, and a refresh token is never presented again) and store nothing; the device poll and the code exchange return that state, the others throw `indeterminate` (`oauth.refresh.indeterminate`, `oauth.client-credentials.indeterminate`, `oauth.registration.indeterminate`, `oauth.exchange.indeterminate`, `aws-identity-center.refresh.indeterminate`), and the error's cause is the `ResponseTooLargeError` (or AWS's own too-large error), which holds none of the body. Only a failure this engine raised itself before sending anything (an input it will not use, a destination it will not reach) is read as refused-before-send. Issuer metadata discovery keeps its own, smaller ceiling of 64 KiB, and a larger document is `malformed`. The same ceiling holds wherever a fetch is handed to the OAuth library instead of the shared client, and wherever an answer that carries or establishes a credential or a session is read by hand: the Supabase Management token requests (a pinned-origin fetch of their own), the authored sign-in's pushed-authorization, token and DPoP-userinfo requests, the authored provider's own device-authorization, token, polling and dynamic-registration requests, the mailbox token, the key set Vercel's forwarded triggers are verified with, the signature agent's key directory, the deployment's own sign-in clients (the issuer an operator configured, the MCP sign-in, and the app's device-login API), Airbyte's application token, Neon's anonymous-project handshake, the Browserbase calls that open a remote browser, and every document the provider-conformance harness reads from the server under test (an answer that is too large or is not JSON is no answer, so the finding that needed it is not met). Jira reads its token answer through the same reader under a 64 KiB ceiling of its own. The Airbyte, Merge and Hasura NDC adapters, whose bodies are provider data and not credentials, refuse a body at the first chunk past their ceiling (4, 8 and 8 MiB) while reading it, with the error codes they always had. `tests/connectors/auth/custom-fetch-gate.test.ts` is a program over the syntax tree and not a text search. It resolves every call into oauth4webapi and jose by what it is bound to (a namespace under any name, a named import, an alias), derives from the libraries' own type declarations which functions can reach the network (including the ones with no `Request` in their name, such as `validateApplicationLevelSignature` and `createRemoteJWKSet`), and fails any call whose options do not resolve to the bounded transport, any custom fetch whose answer does not go through `boundResponse` unread (a body read first, a copy of it bounded afterwards, a branch that returns the answer raw), and any import form that hides a call from it (a dynamic import, a require, a re-export, the namespace used as a value). There is no ledger of exceptions for these. The builders it trusts are checked against their own source on every run, and it carries twenty-five sources it must refuse and four it must accept. Its second half lists the response bodies the host still reads by hand: each is data from a provider or a service of the deployment's own, or a body from a caller, with the reason it is not a credential or a session, and the count only falls. The ceilings bound size and not time: a body that trickles in is cut off by the request's abort signal where the read happens under it (the OAuth transport reads under its request's signal) and not otherwise (the Airbyte, Merge and Hasura adapters read after they have cleared their request timer, which they did before this change as well). The ceiling is generous on purpose: the largest legitimate OAuth answer among the repository's doubles is 1,804 bytes (a discovery document; tokens reach 885 and key sets 605), measured by wrapping `fetch` while every connector suite and the OAuth suites outside them ran (3,938 responses), and the recorded Vercel discovery document is 2,154 bytes, so 1 MiB is over 480 times the largest and 4 times the largest is under 9 KB. A response, an error or a log line never carries a token: the connector error keeps no part of a response the OAuth library attaches to its own failures.

**Disconnect ends the sign-in at the provider, best effort.** A local (or broker) disconnect first asks the adapter to end the sign-in session it holds, just before custody is released, and reports what came of it on the result as `release`: `{ revoked, reason }`, where `revoked` is `true` (the provider acknowledged), `false` (tried, not acknowledged) or `"unavailable"` (nothing to try with), and `reason` is a stable code that holds no token, no body and no provider text. The disconnect never waits on the answer for more than 10 seconds and never fails because of it: an adapter that throws, hangs or answers outside that shape is reported as `session.release.failed`, `.timeout` or `.invalid`, and local release goes ahead. The `upstream` scope is unchanged: it asks the adapter to end the grant and reports that as the `upstream` outcome, once. AWS: the portal's `Logout` ends the sign-in session; role sessions already issued run to their own expiry, and the result never claims otherwise (`aws-identity-center.release.session-ended` says the session ended, nothing more), and the OIDC API has no operation that revokes a refresh token, so that token is dropped with custody and is not known to be ended. Vercel: the refresh token and then the access token go to the revocation endpoint (RFC 7009) with the `none` client's `client_id`; the issuer policy `vercelAccountIssuerPolicy()` has this on, and `{ revoke: false }` pins it off, which the result says (`oauth.revoke.disabled`). Reasons for Vercel: `oauth.revoke.applied` (true); `.refused` (a 4xx or 5xx answer), `.unreachable` (nothing listening, before anything was sent), `.indeterminate` (sent, no usable answer: a dropped connection, a timeout), `.partial`, `.credential-mismatch`, `.unresolved` (the issuer's metadata could not be read), `.busy` (custody would not let the revocation read the credential just now), `.rotation-in-flight`, `.failed`, `.credential-gone` (false); `.disabled`, `.no-endpoint` (the metadata names no revocation endpoint), `.no-token`, `.no-session` (unavailable). The revocation endpoint's acceptance of a `none` client and its answer for each token are assumptions (`VERCEL_ACCOUNT_ASSUMPTIONS`), served by the double and not confirmed at Vercel. A sign-in the provider has itself ended or refused to renew (an expired or rejected session) is not released: there is nothing live to revoke.

For AWS the reasons are `aws-identity-center.release.session-ended` (true: the portal answered 2xx); `.refused` (the portal looked at the request and did not accept it: a 4xx other than those below), `.unreachable` (nothing listening, before anything was sent), `.indeterminate` (sent, and the portal did not process it or no usable answer came back: a 408, 425, 429 or 5xx, a timeout, an abort, a body over the ceiling or of the wrong shape), `.busy` (custody would not rotate the session just now), `.credential-gone`, `.rotation-in-flight` and `.failed` (false); `.session-gone` (a 401: the portal says the session is unknown, lapsed or already logged out, so there is nothing left to end), `.no-token` and `.no-session` (unavailable). The upstream scope reports the same answers as `applied` (2xx), `not-attempted` (`.session-gone`: nothing was done to a session that was not live), `indeterminate` (`.indeterminate`) and `failed` (the rest). The 401 reading is an assumption the double serves (`AWS_ASSUMPTIONS`). A release that meets a rotation already in flight (a refresh, or a choice being bound) follows it and ends the session the rotation left, with the new token, rather than reporting that there was nothing to end.

Every sign-in the connection holds is released, in parallel inside the same 10 seconds: its own, and the one a choice is waiting on (see above), which is dropped from custody whatever came of its release. The combined answer is a failure if any attempt failed, else an acknowledgement, else "nothing to try with"; a waiting sign-in whose custody record is already gone (the choice expired or was refused) is not a failure of this disconnect and is left out. While another local connection still lists the same upstream grant (`sharedWith`) the provider is not asked at all, because ending the session would end it for that holder too: the result is `release: { revoked: "unavailable", reason: "session.shared-grant" }` and the local credential is dropped as before. The disconnect that removes the last holder asks. (No adapter here shares a grant between connections, so this is a rule for the ones that will; sharing is found by listing every holder of each external id, so the older holder's disconnect finds the newer one as the newer finds the older, and the `disconnect.shared-grant` guard for the other scopes finds it the same way.)

The disconnect fences the connection (advances its generation), may talk to the provider for seconds and only then writes the closing lifecycle, so anything that wrote the connection meanwhile (a verify, a poll, a completion already running) has moved its revision. The closing write is made up to six times (the first and five retries, each from a fresh read); a connection that is no longer the generation this disconnect fenced is someone else's and is returned as it is, and a credential a concurrent write put on the record is revoked too, so the tokens are never dropped and the provider told while the record still says `active`. The administrator's revoke closes the same way. The result says which of the two the disconnect was: `local: applied` when it closed the record, `already-closed` when another disconnect had closed it first, `superseded` when a reconnect had taken the connection over (the view is then the reconnect's, not a closed one); what the disconnect held was released in each case.

**Vercel: the two legs stay apart.** Vercel Connect has a management leg (connectors and project links, administered with a team token) and a workload leg (what a deployment presents to obtain provider tokens). The sign-in feeds only the management leg, in place of a pasted token. The Connect adapter takes an optional `managementToken` source, which a host supplies through `ConnectorHostPorts.vercelManagementToken` built with `accountManagementSource({ account })`, where `account` finds the calling person's `vercel-account` connection as a call context. The lease it returns names the custody record, never copies the token, and is checked: a connection that is not the caller's own, in the caller's tenant, is refused; a sign-in bound to another team than the configured one is refused; a connection that is not active (expired, disconnected, awaiting a person, or unsettled) is refused with `vercel-account.management.session-expired`, `.sign-in-required` or `.sign-in-unsettled`, and the configured team token never stands in for a person who has a sign-in; only a lookup that finds no connection at all leaves the configured management token (if any) to serve; the Connect provider itself checks that whatever lease any source returns belongs to the calling person (`vercel.management.lease-not-owner`); and the workload credential never takes a lease. Nothing in the server composes the two connections on its own.

**What a live run must still check.** Each of these is an assumption the doubles serve as written in `AWS_ASSUMPTIONS` and `VERCEL_ACCOUNT_ASSUMPTIONS`, not something read from the provider:

- AWS: the portal host `portal.sso.<region>.amazonaws.com`; `RoleCredentials.expiration` as epoch milliseconds and `clientSecretExpiresAt` as epoch seconds; `slow_down` growing the interval by five seconds; `invalid_grant` for a wrong or used device code; a refresh token issued only to a client that registered the grant and a scope, and single use and rotated (the CreateToken page says only "if present"); 404 for an unassigned role; 401 for a lapsed token. That another client's token is refused is the double's own rule and is in tension with the OIDC Welcome page, which says the tokens grant access to all of a person's account entitlements, not a particular application: the held token's breadth is everything the person is entitled to, and the binding's account and role list is what narrows the connection.
- Vercel: the device authorization endpoint's request and response and the verification page (the discovery document advertises the endpoint and the grant; the Manage-from-dashboard page refers to the device authorization flow for dashboard applications but no page describes the request or response); that an application made on the dashboard may use the device grant (`vercel login` may use a client of Vercel's own); that a `none` client is accepted at the device and token endpoints (the dashboard page offers `none`, the discovery document lists no such method); the error code for a replayed code or refresh token; paging of `GET /v2/teams` by `until` (inclusive, next the last team's createdAt minus one); the full rather than `limited: true` form of `GET /v2/user` and `GET /v2/teams` for a token holding only identity scopes (the schemas do not model the limited form); the 401 for a removed application and `invalid_scope` for an unknown scope; and that Vercel Connect accepts a device-grant token on its management endpoints at all (the permissions page calls API permissions a private beta). The Connect double models that acceptance.
- Revocation and Logout: that Vercel's revocation endpoint accepts a `none` client's `client_id` with no secret, answers 200 for a token it does not know, and ends only the token it is given (so both tokens are presented); and, for AWS, that `Logout` answers 200 for a live session and 401 for one that is over, and that a refresh token is not known to stop working after it. A disconnect reports each outcome on `release` either way; the doubles serve these as written, and a live attended run is what would confirm them.
- Vercel registers no client dynamically: the generic client resolution registers only a method the issuer's metadata lists, and Vercel's lists no `none`, so against the recorded discovery document an RFC 7591 registration of a public client is refused (pinned in `tests/connectors/vercel-account/wire.test.ts`).
- Vercel's token narrows nothing: it reports granted scopes, not the permissions the person holds in the team. The team binding says what the connection is for, not what the token can do.
- Authorization code with PKCE ("Sign in with Vercel") is not a second implementation here. It is the generic authorization-code family under another issuer policy, so adding it would duplicate that mechanism; it is a documented non-goal.

## Remote browser and Agent2Human

`RemoteHumanBrowser` hands a person a remote browser tab for **any** connector's login. It automates only the trusted broker navigation - it opens the connector's own human route in the remote browser, with a private cookie scoped to that route, and waits for the route to send the tab to the provider - then yields provider login and approval to a person through the provider's live view. The connector supplies the route (`HumanTakeoverRoute`: human path, cookie scope, destination origin, instructions); GitHub's registration/installation scenario is `githubHumanTakeover(id)` and is no longer built into the browser. No generic browser tools, screenshots, DOM extraction or recording are exposed to the model. Takeover completion is not authentication proof; the connector's callback and verification still decide.

Three providers mint the takeover URL (`src/server/live-view.ts`):

- **Cloudflare Browser Run** - `Cloudflare.getLiveView`, plus `Cloudflare.handoff` for its [human takeover](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/) banner. `CloudflareHumanBrowser` is `RemoteHumanBrowser` configured for it.
- **Browserbase** - the session debug endpoint, preferring the live view of the waiting tab over the whole browser.
- **Any CDP endpoint** whose operator runs a live view - an `https://` template with `{targetId}`, filled with the tab's CDP target id (`CEREMONY_BROWSER_CDP_LIVE_VIEW_URL` for the executor, validated at boot and never quoted in errors).

Every takeover URL must be `https:` with no userinfo. Control URLs stay out of results, pages, events and model-visible values; they are encrypted at rest and resolve only through an authenticated human route (`humanUrl`, or a `no-store` redirect). The reference CLI enables Cloudflare only when `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` are configured. No paid resource is activated automatically. Remote failure preserves the same ceremony's own-browser option. Active remote sessions close on cancellation/expiry; process restart cannot reattach their CDP event listeners. Human windows expire after five minutes.

The isolated authorization browser uses the same minters for the remote browsers it opens: when an authored connector's login waits on a person (a challenge, a passkey, a missing input) in a remote browser that offers a live view, the authored human route shows **Take over the provider page in a live browser**, and `?live-view=1` redirects - `no-store`, `no-referrer`, from the authenticated route - to the provider's live view of that tab. A local browser offers no link.

### Remote isolated browsers for authored connectors

The isolated authorization browser (`createAuthorizationBrowser`) launches a local Chromium behind the local egress proxy by default. It can instead drive a remote browser: Browserbase (`BROWSERBASE_API_KEY` + `BROWSERBASE_PROJECT_ID`), Cloudflare Browser Run (the same `CLOUDFLARE_*` pair), or **any Chrome DevTools Protocol endpoint** — Steel, browserless, or a Chromium the operator runs with a debugging port — via `CEREMONY_BROWSER_CDP_URL` and optional `CEREMONY_BROWSER_CDP_HEADERS` (a JSON object presented on the websocket upgrade). The endpoint must be `wss://`/`https://`, or `ws://`/`http://` on loopback only, with no userinfo; credentials go in the headers. `remoteBrowserOptionsFromEnv` validates all of this at startup, so a malformed value refuses to boot instead of failing a later login, and its errors never quote a value.

**Every remote browser requires `CEREMONY_BROWSER_REMOTE_PROXY`.** A remote browser's traffic leaves from someone else's network, where the local egress proxy cannot see it, so the operator-vetted proxy is its only containment. Without one, the executor opens nothing and reports `browser-unavailable`; this is deliberate and is not relaxed for any provider. The proxy URL must be `http(s)://` without userinfo; use `CEREMONY_BROWSER_REMOTE_PROXY_USERNAME`/`_PASSWORD` for proxy credentials. The proxy has to be reachable _from the remote browser_, and whether it actually contains egress is the operator's claim to verify — Ceremony only guarantees that every context it opens is configured to use it, with loopback not bypassed.

Evidence: `tests/browser-remote-cdp.test.ts` connects to a separately spawned local Chromium through its debugging port and asserts, from a fixture forward proxy's own record, that the provider was reached through the configured proxy. `tests/live-view.test.ts` checks the takeover-URL rules, the template and Browserbase minters against a real local tab (Browserbase's API is a fixture), and a generic `RemoteHumanBrowser` takeover end to end over a local browser, including that no database file holds the control URL; `tests/cloudflare.test.ts` keeps the GitHub/Cloudflare scenario. No hosted CDP provider, Browserbase account or Cloudflare account was exercised, and no live view was opened by a person.

#### Two browser systems, one set of rules

There are still two browser subsystems: the **authorization executor** above (`createAuthorizationBrowser`, used by authored connectors, with its egress proxy and remote providers) and the **login driver** (`runCeremony` with `browser-page.ts`, `browser-interpreter.ts` and `browser-login-service.ts`, used by login plans and recorded ceremonies). They now share the parts that decide where a person's credential may go and how a person is brought in:

- **Windows.** The rule for adopting a window the page opens is one module, `browser-windows.ts`, used by the driver's page adapter and by the executor. The executor adopts only windows at origins the connector declared; see [the workflow studio](workflow-studio.md).
- **Live view.** Both the executor's remote browsers and `RemoteHumanBrowser` mint takeover URLs through `live-view.ts`.
- **Hand-offs.** The login driver's `HumanParticipation` can be backed by the store (`createBrowserHandoffs`, see [handoffs](browser-login-sessions.md#handoffs)), so a person can answer from any process. The executor's paused sessions are still held by the process that opened them; the authored route's durable `pending` flag and `session-expired` blocker are what survive a restart there.

What is not converged: the executor still drives pages with its own deterministic and inferred drivers rather than through `createPlaywrightCeremonyPage`, so its element revalidation, recording and issued-value reading remain the driver's alone.

`Agent2Human` implements the signed AUTHORIZE/RESPONSE slice of [Twilio Agent2Human](https://github.com/twilio-labs/Agent2Human): gateway discovery, canonical JSON, detached Ed25519 signatures, stable pending delivery IDs, pinned response verification, principal/correlation/expiry/replay checks. Configure `ReferenceOptions.live.a2h` programmatically with gateway origin, agent/key IDs, private and pinned gateway keys, API credential and an authenticated `recipient(owner)` resolver. Contacts are never model-provided. Configure gateway response delivery to `POST /api/live/a2h/:instanceId`; this reference does not negotiate a callback subscription for you.

Approval requests verification; it never grants a connection. Denial cancels the parent. The implementation does not claim complete A2H conformance: RESULT delivery, gateway cancellation and production transport/reconciliation remain outstanding. Cross-device delivery requires a host login that restores the same principal; the anonymous-cookie example alone cannot provide that. Without a configured transport, users continue directly in their browser. Private app recovery uses the collector, not remote browser capture.

## Authored secret connectors and confidential clients

Authored API-key, Basic and form connectors, and authored OAuth connectors with a confidential client, collect their secret on the run owner's native page and keep it in encrypted server custody; see [the workflow studio](workflow-studio.md) for the verification declaration, the allowlisted authorization parameters and the client-secret rules. Evidence: `tests/authored-secret-connectors.test.ts` and `tests/authored-confidential-client.test.ts` drive the real operations and human route against synthetic provider responses in memory. No live provider was exercised.

## Hooks and evidence

Browser success/failure hooks stay best-effort and secret-free. With durable storage, state transitions and action outcomes also produce encrypted outbox records. Deliver them from a trusted worker:

```ts
await db.deliverEvents(async (event) => {
  await hostEvents.publish(event); // Consumer deduplicates event.eventId.
});
```

Delivery is at least once; failure retains the record. Action events carry `action`; transition events describe state. Neither carries submitted values, provider URLs or credentials. Always re-read authorized state before acting on an event; operation success is not connection success.

Local verification covers real cryptography with fixture HTTP responses, restart, ownership, callback replay, reference misuse, durable event redelivery, MCP message secrecy, prerequisite bypass rejection and the actual browser UI. Packed React/Vue consumer tests cover external composition. Still required: an authorized real GitHub registration/install flow, Cloudflare takeover, a configured A2H gateway, and telemetry isolation in each actual MCP host. The approved design's broader multi-connector prerequisite engine is not complete.
