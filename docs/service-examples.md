# Real-service ceremony examples

Reviewed 2026-09-08 against the primary sources below. Available services across simulation and live modes cover every member of the runtime's `flowKinds`. All examples execute through the shared client, controller, native WebMCP actions and success/failure hooks. They render functional OpenUI ceremonies, not static screenshots.

The default collection now offers GitHub App registration/installation, Stripe key verification and Supabase project sign-in through actual provider SDKs. Registration and missing configuration are part of the selected ceremony, not separate experiences. [Live authentication](live-auth.md) documents their exact boundaries and host setup. The table below describes the explicit developer harness at `/?mode=test`; it is not the normal connector collection. Jira and Neon remain test-only until their live prerequisite and recovery paths are ready.

**Execution is local simulation.** Vendor names identify documented methods, not a live account connection or certified adapter. Do not enter real credentials in the demo. Provider-specific application registration, endpoints, secrets, wire formats and storage are host responsibilities.

The inventories are curated examples, not every login option offered by each vendor. No invented `api.read` permissions are attached to Stripe, Jira, Supabase or Neon. Empty OAuth scope lists do not imply unlimited access.

Jira's Basic example is only the labeled developer harness, not the design for a distributed live connector. Rechecked on 2026-09-10: Atlassian's [current integration guidance](https://developer.atlassian.com/cloud/jira/platform/basic-auth-for-rest-apis/) requires a shared distributable 3LO app instead of collecting customer API tokens or instructing each customer to create an individual app. Integration registration therefore belongs to an authorized integration owner; end users should reuse that setup and complete provider-owned account/consent steps. This live 3LO ceremony is not implemented yet. For explicitly permitted script profiles, [scoped API tokens use the gateway/cloud-ID URL](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account), not the unscoped site URL; the two must not be silently interchanged.

## Why Neon has a separate adapter

The original auth.md adapter implements the WorkOS-documented email/code claim grant. Neon's published profile instead uses project claim endpoints, a provider-owned organization selection page, and a `reconciled` completion flag. These are not interchangeable protocols.

`createNeonAdapter` is exported from `@ceremony/auth/server`. Its state and secrets stay in the server adapter/credential store. `claimFields: []` declares that the claim confirmation collects no identity fields in the host UI; omitting `claimFields` retains the original email/code profile. Both use the same `claim`, `submit`, `navigate` and `read` actions, including WebMCP and hooks.

After successful reconciliation the adapter replaces its stored credential with a project-ID-only record. Hosts must implement replacement semantics for `CredentialStore.put`. It does not fetch a database connection string, rotate provider-side credentials itself, or claim an authenticated API session after transfer. Project provisioning and claim endpoints are simulated locally in the example; no real cloud resources are created by tests.

The original email/code profile still has protocol tests. We did not relabel Firecrawl or Resend as anonymous providers: [Firecrawl's auth.md](https://www.firecrawl.dev/auth.md) explicitly excludes anonymous/claim flows, and [Resend's auth.md](https://resend.com/auth.md) describes user-supplied API keys rather than agent registration.

## Coverage boundary

The six runnable families are API key/token, HTTP Basic, forms, OAuth code/PKCE, device authorization and auth.md anonymous/claim. The broader [auth catalog](auth-catalog.md) still lists unimplemented profiles, including MCP authorization, identity assertions/agent JWT, service-auth entry, OIDC, SAML, passkeys and workload federation. This change does not turn those entries into working adapters. For example, [Linear documents MCP OAuth with discovery/registration](https://linear.app/docs/mcp), and Firecrawl documents ID-JAG registration; neither is satisfied by relabeling a generic OAuth button. Those require their actual adapters and protocol tests before being offered as executable methods.

## Verification

The manifest test checks exact service IDs and complete runtime-family coverage. Browser tests execute GitHub OAuth/device/token, Stripe key entry, Jira Basic, Supabase form and Neon's provider-owned transfer. Protocol checks retain state/PKCE, replay, denial, cancellation, expiry, signed-assertion and credential-isolation coverage, and add Neon reconciliation, 401 assertion re-exchange and pre-claim secret disposal. Packed React and Vue consumer fixtures use Stripe to verify host reuse independently of the demo shell.
