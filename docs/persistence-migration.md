# Transactional persistence

The teaching server uses `AsyncCeremonyStore`. PostgreSQL is the shared deployment adapter; SQLite is the local adapter. Both await the transaction callback before commit and roll back a rejected callback. Network/model/provider work must happen outside a transaction. A transaction object is invalid after its callback returns. Do not nest a store transaction inside its own callback.

`PostgresCeremonyStore` accepts a `pg` Pool configuration. Configure verified TLS for a remote database through that configuration. Run `migrate()` before serving requests. The migration creates `ceremony_records` and `ceremony_claims`; it is additive and does not rewrite the legacy `records` table. Migration does not grant database access or provision a database.

The old `CeremonyDatabase` remains a synchronous compatibility API for existing consumers. It is not a distributed store and must never receive an async transaction callback. Migrating an existing host requires reading its authenticated owner mapping and validating each legacy payload, then inserting it using `tx.put({ tenant, kind, id }, value, null)` in the new store. Do not turn anonymous legacy owner cookies into production principals. Existing live sessions require reauthentication before migration; no automatic cross-principal credential migration is provided.

Record kinds are a closed list (`recordKinds` in `src/server/persistence/index.ts`); a key with an unknown kind is refused, so a new kind is added by appending it to that list, never by reordering or renaming one. The record and claim tables are generic, so a new kind needs no SQL migration and an existing database keeps every row. Each kind added for connectors carries `schemaVersion` in its value. `connector-oauth-registration` (appended after the event kinds) holds RFC 7591 dynamic client registrations, one insert-only record per tenant, issuer, redirect URI and host origin; its value includes the issued client secret and registration access token and is encrypted like every other record. Key rotation and backups must cover it like credential records. A composed connector runtime uses it by default for dynamic registration; a host that supplied its own registrations store keeps using that one, and nothing migrates records between them.

All record payloads, including events and outbox bodies, use AES-256-GCM. Authenticated associated data binds tenant, kind, ID, revision, and key identifier. Only opaque identifiers, kind, revision, worker identity, generation, and expiry are indexed in plaintext. Never use email addresses, provider tokens, private URLs, or other protected values as identifiers. Keys are supplied independently of the database; database backups must not contain key material.

For rotation, configure the new current key together with retained old decryption keys. Read bounded ID-ordered pages and invoke `rotateRecords(store, tenant, kind, pageSize, afterId)` for each page. Keep old keys until every tenant/kind and retained backup has migrated or expired. Rotation increments revisions, so coordinate active writers and refresh stale snapshots. Unknown keys and tampered ciphertext fail closed with a bounded error.

Commit state, safe semantic events, and outbox entries in one transaction. A consumer processes outbox work outside the transaction and acknowledges it with revision-CAS deletion. Delivery is at least once: consumers must deduplicate a stable continuation/event ID. An acknowledgment lost after an external effect is not proof the effect failed.

`AsyncPrivateCollectionBroker` binds each collection to its authenticated tenant/subject, exact operation/version, purpose, provider, run/node, revision, and declared field set. Call `consumeIn` in the command-admission transaction; retries of that same command recover the protected values until its bounded recovery lifetime ends. A different command cannot consume the reference. `complete` deletes the values and retains only the protected command tombstone. `purgeExpired` removes expired private material without deleting audit or command records. Private references and consume associations are server-only, not model tools or portable recipe inputs. A host must recheck current authorization before every recovery or provider effect; parsing an `ActorContext` is not authentication.

PostgreSQL idle-client failures set a bounded degraded health status rather than emitting an uncaught driver error containing connection configuration. The next successful transaction resets health. Connection, query, and migration failures expose only fixed error messages. This does not replace database monitoring or host-level safe error handling for domain callbacks.

Workers claim a key and receive a monotonically increasing fencing generation. Before committing effects, call `assertFence` in the same transaction as the conditional state/evidence write. Heartbeat and cancellation use database time, not a browser timestamp. A claim does not make an external provider exactly-once; uncertain effects require provider-specific reconciliation. Cancellation increments the generation; run cancellation state must also be checked by the command service before future claims.

Back up PostgreSQL using its consistent snapshot tooling, retaining encryption keys separately. For SQLite, stop writers and close the store before copying the database, or use SQLite's online backup mechanism; copying an active WAL database file alone is not a backup. Test restore with the configured keys before accepting traffic. Restored workers must not overlap an active deployment against unreconciled provider effects.
