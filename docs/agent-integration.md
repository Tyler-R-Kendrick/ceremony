# Agent integration

The server-only AI SDK `ToolLoopAgent` proposes registered node advancement. It cannot supply credentials, bindings, endpoints, verifier code, tenant identity, or an approval. `ProtectedCommandService.advance` loads the pinned plan and rechecks host authorization; UI and agent execution use that authority service. Native WebMCP remains an optional transport, not an authentication mechanism.

Hosts can register connection entry points through `createTeachingRuntime({ connections })`: a read-only map from connector ID to its deterministic `definition`, verified `outputContract`, and host-policy `revalidateOperation`. Omitting the map preserves the GitHub default; an explicit map advertises only its registered IDs. Registration is server configuration, not an imported recipe or model capability. Each operation must still match the host-derived provider/profile and pass command authorization. The capabilities, Connect, and agent routes use this same registration. Published-recipe execution accepts `connectorId` (omission preserves the existing GitHub HTTP contract). Registering an ID does not implement its provider operations, human collector, or certify a live connection.

A chat client reaches the same teaching operations over the MCP endpoint, not only through the browser: it can author a connector draft, record a run as a demonstration (`ceremony_connect` with `teach`, or `ceremony_demonstration_start`), compile the recording into a recipe draft, compose published recipes into a new draft, and execute a published recipe pinned by version and digest. The tools call the same service operations as the HTTP routes (`src/server/teaching-operations.ts`) and are offered only to actors whose capabilities could use them. Review and publication have no agent tool on any transport: a draft an agent produces runs only after a person reviews and publishes it. See [the MCP endpoint](mcp-endpoint.md#what-the-endpoint-registers) for the tool list. The evidence is local: the MCP tests drive an in-process handler against fixture operations, not a live provider.

`CEREMONY_MODEL_URL` remains a full OpenAI-compatible `/chat/completions` endpoint; `configuredModel` explicitly adapts it to the installed provider SDK base URL. `CEREMONY_MODEL` is required when enabling a model; `CEREMONY_MODEL_KEY` is server-only. Gateway is enabled only by explicit trusted configuration, with an explicit model ID. No configured model means no paid service fallback. Model redirects are forbidden for compatible endpoints.

A native Anthropic provider is available through the official `@ai-sdk/anthropic` package. Set `CEREMONY_MODEL_PROVIDER=anthropic`, an explicit `CEREMONY_MODEL` (there is no default model ID), and server-only `CEREMONY_MODEL_KEY`. `CEREMONY_MODEL_URL` is optional for this provider; when set it is the full Messages endpoint ending in `/messages` (for example a loopback fixture or a trusted proxy), and it passes the same URL checks as a compatible endpoint. Unset, requests go to `https://api.anthropic.com/v1/messages`. The broker never reads `ANTHROPIC_API_KEY` or `ANTHROPIC_BASE_URL`: the key is required explicitly and the base URL is always passed, so an operator's shell credential cannot become the broker's paid route. The provider SDK may reach only the configured URL and never follows a redirect. `CEREMONY_MODEL_PROVIDER` cannot be combined with Gateway routing. `modelConfigurationFromEnvironment` reads these names for the hosted runtime; the example server's template generation remains compatible-endpoint only.

`AgentCoordinator` reserves durable per-run/per-turn budgets before inference. The defaults allow 16 model calls and 64 requested tools per run, eight requested tools per turn. Unknown tool names count. Existing complete access, human waits and absent model configuration require zero model calls. Stopping the assistant is persisted and checked before later tool execution; it neither cancels the connection nor revokes provider access. An interrupted turn with uncertain completion is not silently replayed as a fresh turn.

The model has three tools, and every call counts against the same budgets:

- `advance` proposes a registered node advancement, as before.
- `snapshot` rereads the current run through the same positive-allowlist projection (run and node IDs, operation IDs and versions, states, verification, revision). It is read-only.
- `request_human` hands an unverified node to the person who owns the run and ends the turn. It grants and approves nothing.

Calls emitted in one step run one at a time in emission order, so a wait reached by one call ends the turn before the next acts. Each step's context is the fresh projection plus the previous step's coordinator-built results. A failed `advance` reports one fixed code: `denied` (authorization), `invalid` (rejected input), `conflict` (stale revision; reread before retrying) or `transient` (rate limiting or any unrecognised failure; reread before retrying). A rejected call, including an invented tool, is reported only as `{tool, error: "invalid"}`, with an invented name replaced by `unknown`. Error messages, invented tool names and tool arguments never return to the model.

A turn that ends on a person records a handoff descriptor with the turn. That covers a run that reached a human wait, verification or an uncertain outcome, a `request_human` call, and a turn that stopped without progress. `AgentCoordinator.turnOutcome` returns it, and the owner-authenticated status route and status stream include it while the status is `awaiting-human` or `uncertain`. `turn` still returns the enum alone, which is all the Workflow history records. The descriptor holds the run ID, node ID, operation ID, node state and a fixed reason. Only a node that is `awaiting-human` also gets a same-origin `path` to the existing authenticated human route (`/api/v1/teaching/<provider>/<run>/human`, or the host's `humanRoutePrefix`). `<provider>` is the waiting step's own provider, which differs from the run's when the step runs under another connector. The path carries no origin, query, code or token. Opening it still requires the run owner's own session, so the descriptor grants nothing to whoever holds it. Hosts and MCP clients can use it to route the person. It is not an A2H request and not a URL-elicitation grant.

The Vercel Workflow carrier (`src/server/agent/workflow.ts`) uses `use workflow` and `use step`, with a human-wait hook established before each bounded turn. The Nitro host must load `workflow/nitro`; ordinary Vite rendering is unchanged. The workflow history receives run/turn correlation IDs and enum statuses only. Each step creates a worker-owned hosted runtime, restores the recorded initiating actor and current delegation, invokes the same coordinator, and closes its database pool. A hook wake carries `{wake:true}` only and never substitutes for verified provider evidence or current domain authority. Hosted routes must authenticate and authorize the intended run before waking a hook; failed delivery remains pending for durable outbox retry. Domain persistence, effects, revisions, and continuation delivery remain authoritative, not Workflow replay history.

There is no narration or attachment recorder. `validateAgentText` is a bounded pre-egress utility for hosts adding text input: it rejects known protected values and recognizable credential formats without retaining them. This heuristic cannot detect every arbitrary password. Never add protected fields to model context merely because a user opens an assistant. The model receives positive-allowlist domain snapshots; each model step rebuilds its context rather than appending arbitrary model/tool-error history. Free-form model output is not rendered as an authorization verdict. AI telemetry is disabled additionally, not used as the privacy boundary. Configured model/gateway processors may retain the permitted context under the host's processor policy.

The local SDK transport tests use a real HTTP chat-completions fixture, including unknown tools, malformed responses, structured authoring, outage and durable stop/budget cases. A second loopback fixture speaks the Anthropic Messages shape and checks the tools, error codes, handoff, the `x-api-key` header, and that neither the key, ambient `ANTHROPIC_*` values nor private run fields appear in any request body. These are fixture evidence, not a live Anthropic certification. The installed Workflow compiler/local runtime test traverses real PostgreSQL, the hosted runtime, model HTTP, and GitHub preparation; it waits on a durable hook, resumes after stopping the assistant, and verifies the connection remains active with no extra inference. A separate missing-configuration test fails closed. These do not establish process-crash recovery across a deployed platform, live model, hosted Workflow deployment, or attended provider certification. No Eve, Chat SDK, external bot, DOM agent, recorder extension or second agent runtime is installed for this capability.
