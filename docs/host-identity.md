# Host identity integration

`HostIdentityAdapter.authenticate(Request)` is a trusted server integration. It returns the shared `ActorContext` only after authenticating the host session. No browser owner, source, tenant header, recipe metadata, or tool argument establishes identity. Capabilities are `author`, `reviewer`, `publisher`, `executor`, and `admin`; grants to one subject never move with an exported recipe.

The reference `createOidcIdentity(config, persistentIdentityStore(store))` uses oauth4webapi for discovery, authorization code exchange, PKCE, state, nonce, issuer/audience/expiry checks, and ID-token signature validation. `store` is the shared encrypted async persistence adapter. No database transaction spans the provider request. The single-use login state is consumed atomically before exchange; a failed exchange requires a fresh login rather than replaying its code.

Mount `login` at POST `/api/auth/login`, `callback` at GET `/api/auth/callback`, and `logout` at POST `/api/auth/logout`. Login/logout require the exact configured Origin and JSON content type. Register the exact callback with the identity provider. `mapClaims` is host code mapping verified issuer/subject claims to tenant membership and current capabilities. Do not derive administrator membership from an unverified email or a submitted tenant. Separate browser contexts authenticate again and recover the same subject through this mapping, not copied browser storage.

### Tenant and roles in the hosted reference

The hosted reference supplies `mapClaims` for both its browser identity (ID token) and its MCP identity (access token) from one tenancy object in `src/server/hosted/tenancy.ts`, so the two transports cannot disagree about who someone is. Tenant comes from `CEREMONY_TENANT_ID` (every identity in one pinned tenant) or from the signed claim named by `CEREMONY_TENANT_CLAIM`. A token without that claim, or whose value is malformed or names a server-reserved tenant, produces no actor; it is never placed in a fallback tenant. Capabilities come from the claim named by `CEREMONY_ROLES_CLAIM` (default `ceremony_roles`), mapped through `CEREMONY_ROLES_MAP` when set or by capability name otherwise. A token with no roles claim is `executor` only; a present roles claim grants exactly what it maps to; unknown role names grant nothing; a malformed roles claim produces no actor. Either claim setting is a top-level claim name taken whole (URL-shaped names included) or, when it starts with `/`, an RFC 6901 JSON Pointer into nested claims such as `/realm_access/roles`; a pointer walks objects only, and a malformed pointer fails configuration at start-up. `tests/hosted-tenancy-claims.test.ts` pins that grammar. See [production deployment](production-deployment.md#tenants-and-roles-from-the-identity-provider) for configuration. `tests/hosted-platform.test.ts` exercises two claim-derived tenants against real PostgreSQL and a local signed issuer; it is local protocol evidence, not certification against a deployed identity provider.

Production configuration requires an exact HTTPS application origin, trusted HTTPS issuer, client ID, optional server-only client secret, shared persistence, and encryption keys outside the database. `development: true` permits only explicit `127.0.0.1` HTTP fixture origins; it must never be set by a request. Production uses HttpOnly, Secure, SameSite=Lax, host-only cookies. Sessions have a bounded lifetime no longer than the ID token and receive a new random identity after login. Logout removes the server session; it does not revoke upstream provider grants or background delegations.

For each feature route, call `authenticatedActor`, `requireCapability`, resource ownership policy, `reserveRequest`, `assertRequestBoundary`, and `boundedJson` as appropriate. `boundedJson` enforces the real streamed byte count, not only Content-Length. Mount all routes behind these boundaries, including streams, imports, execution and human return routes. Restrict unauthenticated login traffic additionally at the trusted ingress; authenticated request quotas are shared transactional counters.

Consequential operations use `effectAuthorizationDigest` and `authorizeEffect` against a freshly loaded grant. The digest covers tenant, subject, parent run, operation/version, target, configuration, scopes and canonical validated argument digest. It detects material changes; it is not a signature or a grant. Never use hashes of low-entropy secrets as public redaction. Recheck persisted grant revocation after waits and before effects/commits. A session's expiration and a background delegation's revocation are different decisions.

Tests in `tests/identity.test.ts` run real loopback HTTP discovery, token and JWKS endpoints with signed fixture tokens; validate wrong nonce/audience/signature/expiration, callback replay, state forgery, session restoration, logout, capability separation, effect binding, stream size and shared rate limits. This is deterministic protocol evidence, not certification against a deployed identity account. Deployment routes must preserve no-store and no-referrer headers and exclude callback/query, token exchange and cookie content from logs and traces.

Reference: [oauth4webapi OIDC API](https://github.com/panva/oauth4webapi/blob/main/examples/oidc.ts).
