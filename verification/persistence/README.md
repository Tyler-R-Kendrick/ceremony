# Persistence: the lease on a key and the revision check

A TLA+ model of `src/server/persistence/index.ts`, checked with TLC. It covers one `RecordKey`: the lease that workers claim, keep alive, lose and take over, and the record that they write with an expected revision.

**The property.** A worker whose lease on a key was taken over or cancelled can never commit a fenced transaction on its old fence, and a put or delete that names a revision changes the record only if it is still the version the caller read.

**The harm if it breaks.** Two workers both finish the same run, outbox entry or effect, or one silently overwrites or deletes what the other stored: a provider call is repeated, an outcome is lost, a single-use value is spent twice.

`docs/architecture.md:38` makes the promise in the repo's words: "Revisions and worker generations fence stale commits".

Checked at commit `3f4434bdce66cb55f200b43a265dc577ec2b4f54`. `.claude/skills/verify-persistence/SKILL.md` keeps the sync commit.

## Finding F1: a deleted and re-created record took its old revision number again

Closed in `35fb0d1e9c66ec64b14bd1a54a1c16d28bdbff4a`.

Before that commit, `put` with `expectedRevision = null` always stored revision 1, and `delete` removed the row and with it the count. So a record that was deleted and created again was back at a revision that an earlier reader could still hold, and the check `AND revision=$6` could not tell the two records apart: worker A read revision 1, another caller deleted the record and created it again at revision 1, and A's `put(key, value, 1)` or `delete(key, 1)` was accepted on a record A never read. A lease did not help.

What the code does now:

- `delete` (`index.ts:361-377`) removes the row and keeps its revision in `ceremony_retired` (`:371-376`, table `:208-210`).
- `put(key, value, null)` (`create`, `index.ts:264-315`) stores the record one above the key's retired revision, or at 1 if it has none, and removes the retired row (`:310-313`). The INSERT (`:286`) waits for a transaction that is deleting the key; once it holds the new row no other transaction can delete the key, so `retired` is read again after it (`:296`) and the record moves above a delete that committed in between (`:297-309`). The model takes `create` as one step for that reason.
- Revisions are counted per key: `ceremony_retired` has one row per key whose record is deleted and not created again, and the delete of one key never changes the revision another key's record is created at. A key that never had a record starts at revision 1. The migration adds `ceremony_retired` to an older store; revisions of records deleted before then are not known. `encryptedBackup` exports the retired revisions (`retired`, backup version 2, or 3 for a store with a lease base) and `restoreEncryptedBackup` restores them, refusing a key that has both a record and a retired revision; a version 1 backup restores with none (`index.ts:573-709`). The model has one key and leaves backup and restore out.

`FindingRevisionReused.cfg` now holds. `BrokenNoRetiredRevision.cfg` sets `KeepRetired = FALSE`, the code before the fix, and TLC finds the old path again. `replay.mts` replays the path against the real stores: on SQLite across transactions, on PostgreSQL with the delete and the create landing while A's fenced transaction is open. Both refuse the stale put and the stale delete. `tests/persistence-revision.test.ts` and `tests/persistence-revision-restore.test.ts` test the same on both stores, through migration, backup and restore, and with a create that waits for a delete of the key on PostgreSQL.

Callers that carry a revision from one transaction to a later one, such as the OAuth ticket of a run in `src/server/authored-human.ts` (`:360` to `:384`; `:1152` to `:1177`, `:1187`, `:1204`, `:1219`), now get `PersistenceConflict` where they were accepted before; none of them relied on a revision being handed out again. The ticket's own `revision` field (`:368`, `:1129`) is the run record's revision, and run records are never deleted. A caller that takes the revision of a created record uses the one `put` returns: `createDraft` (`src/server/recipes/index.ts`) and the connection store's `create` and `saveConnection` (`src/server/connectors/state/connections.ts`).

## Findings F2, F3 and F4: the lease was safe only by accident

Closed in `117e4336100416b1baf242bb0ce12742139fffc9`, `9978b10f91e2193818b5d0b18a19d29278b5cda4`, `3002fea875a02a062d48531546b82585fd33215d` and `3f4434bdce66cb55f200b43a265dc577ec2b4f54`.

Each is a rule of `Fence.tla` with a `Finding*.cfg` that states it on the code as written and holds, and a `Broken*.cfg` that sets the rule's switch `FALSE`, the code before the fix, and breaks it. `tests/persistence-revision.test.ts` (the tests named "rule 5", "rule 6" and "rule 7") runs each path against the PostgreSQL store.

- **F2, rule 5.** `heartbeat`'s UPDATE named the key only, not the generation, and was safe only because `assertFence` locked the row just before: with the lock taken out, A's `assertFence` passed, someone cancelled the key and B claimed it with the same worker string, and A's UPDATE gave B's row A's expiry. The UPDATE now changes the row only where generation and worker are the fence's (`AND generation=$5 AND worker=$6`), and a heartbeat that changes no row is a `PersistenceConflict` (`index.ts:446-455`). `FindingHeartbeatWithoutRowLock.cfg` takes the row lock out (`LockFenceRow = FALSE`) and holds. The test strips the row lock from the holder's statements and runs the takeover right before the UPDATE: the heartbeat fails and the new holder's row is unchanged.
- **F3, rule 6.** `claim` reads the clock (`index.ts:403`) and then runs the upsert, which waits while another transaction holds the row. The lease used to be `time + durationMs`, so a claim that waited past its duration returned a fence that had already run out. The upsert writes the lease from the database clock (`${clock}+$5`, `index.ts:413-416`), and `time` only decides whether the lease on the row has run out (`$6`). That is not enough for the INSERT of a key with no row: PostgreSQL computes its values when the statement starts, then waits on another transaction's uncommitted insert of the row, and if that transaction rolls back it writes the expiry it computed before the wait. So once the upsert holds the row, `claim` sets the lease again from the clock (`UPDATE ... SET expires=${clock}+$4`, `index.ts:428-438`). `FindingClaimReturnsExpired.cfg` holds. The "rule 6" test holds an existing row in a fenced transaction for 1.5 s while a claim of 1 s waits on it; `tests/persistence-claim-insert.test.ts` holds an uncommitted insert of a free key for 1.5 s and rolls it back while a claim of 1 s waits on it. In both the fence the claim gets passes `assertFence`.
- **F4, rule 7.** `restoreEncryptedBackup` used to write each claim row of the backup at `generation + 1`, and a key with no row in the backup got none, so workers that claimed on the first store after the backup held generations that the restored store handed out again. Now a generation is the store's lease base plus a count of the key's claims and cancels, which stays below `leaseSpan` (2^22, `index.ts:108-129`); a claim that would reach it is refused with `LeaseGenerationsExhausted` (`:414`, `:417-426`), and a cancel there keeps the generation (`:462`). The base is the one row of `ceremony_lease_base` (`:211`, read at `:214`), 0 for a store that was never restored. A restore takes as its lease epoch the second of the database clock it runs in, counted from 2025-01-01, and waits until that second is above the epoch of the store the backup came from (`:657-679`; a backup of a store with a base is version 3 and carries it, `:616-632`), writes it (`:684-686`), and writes each claim row of the backup at the base + 1 (`:692-695`). A key's first claim or cancel also starts at the base + 1 (`:414`, `:462`). Every generation a store hands out lies in its own epoch's span: every generation of the first store, before or after the backup, is below the restored base, and two restores that run in different seconds, of one backup or of two, hand out no generation in common. So no fence from before a restore names one the restored store hands out, also when the same backup was restored before, the store it was restored into handed out fences and was then lost. An earlier fix took a base that was the source's + 1 plus a random step of 1 to 1,024, so two restores of one backup shared every generation with probability 1/1,024; the second restore is now in the model (`RestoreEpochFromClock`, `BrokenRestoreEpochNotFromClock.cfg`). The model has the base as `LeaseBase`, the lease epoch times `MaxEpoch + 1`, since no store in the bounds counts past `MaxEpoch`, and the epoch of a restore as the clock `now`. `FindingRestoreReusesGeneration.cfg` holds. The "rule 7" test does the path for a key in the backup and a key that is not; `tests/persistence-lease-epochs.test.ts` restores one backup twice a second apart, and restores a backup of a restored store within the second of its restore.

## What the model also shows (not rule breaks)

- **A fenced transaction can commit after the lease's time ran out.** `assertFence` checks the clock once (`index.ts:260`). If the transaction stays open past the expiry, it still commits. Nobody can take the lease over meanwhile, because the claim row is locked until the transaction ends, so rule 1 holds.
- **Two checks are not needed for these rules.** With the generation check in place, the comparison `row.worker !== fence.worker` (`index.ts:259`) and the `generation+1` in `cancel` (`index.ts:462`) each refuse nothing more. They are in the model, but there is no broken variant for them, because removing either breaks no rule.

What the bounds mean:

- `Duration`: the `durationMs` of `claim` and `heartbeat`, in clock ticks. The code allows 1 to 300,000 ms (`index.ts:316-319`).

- `Fence.cfg` and `RevisionNoDelete.cfg` treat the processes as interchangeable (TLC symmetry).

A pass covers these bounds and this model, not the whole system.

## What one step of the model is

One step is one SQL statement, or a run of statements that no other transaction can come between.

- **SQLite.** `transaction()` runs the whole callback between `BEGIN IMMEDIATE` and `COMMIT` (`index.ts:485-529`), one transaction at a time per store object (`tail`, `:472`, `:527`) and one writer at a time per file. Its runs are the runs of the model in which the steps of one transaction come one right after the other.
- **PostgreSQL.** `transaction()` runs the callback between `BEGIN ISOLATION LEVEL READ COMMITTED` and `COMMIT` (`index.ts:735-762`), so at the default level, READ COMMITTED, transactions interleave statement by statement. The model interleaves them the same way, with two things joined into one step:
  - `assertFence` reads the claim row with `FOR UPDATE` (`index.ts:241`, `:247-253`). From there to the end of the transaction no other transaction can change that row: `claim`, `cancel` and another `assertFence` on the key wait. The model's `lock` is this row lock. `replay.mts` checks on PostgreSQL that a `cancel` waits.
  - A write that is not yet committed is not visible to anyone, and holds its row. So the model puts each write and its `COMMIT` in one step. A statement that had to wait decides on the row as it is after the other transaction committed.

| `Processes`, `SharedIdentity`                                          | The worker processes, and whether they pass one `worker` string to `claim` (`hosted/a2h.ts:39`; `tests/security/fencing-generation.test.ts` is the same case as a test).                                                                                                                                                                                                                                |

## Assumptions

- PostgreSQL runs at READ COMMITTED: the store opens every transaction with `BEGIN ISOLATION LEVEL READ COMMITTED` (`index.ts:750`), whatever the database default. A create that waited on a delete has to see that delete when it re-reads the key's retired revision; under REPEATABLE READ it would not, and would reuse a revision. `tests/persistence-revision-restore.test.ts` runs that race on databases that default to repeatable read and to serializable.
- Each store has one clock that does not go backwards. Both backends read the database's own clock, never the worker's.
- Two restores run in different seconds of their databases' clocks, and those clocks agree to within the time between the restores. A restore takes its lease epoch from the second its database's clock reads (`index.ts:662-679`), so two restores in the same second, of one backup into two databases, take the same base and can hand out the same generations. `RestoreBackup` lets the second restore run only at a later clock reading than the first. A restore waits at most 3 s (`epochWaitMs`) for its clock to pass the epoch of the store the backup came from, and is refused after that.
- A caller keeps `assertFence` and its writes in one transaction, and does not catch `PersistenceConflict` and commit anyway. The model's fenced commit exists only after `assertFence` passed in that same transaction. Whether each caller does this is not checked here.
- An error other than `PersistenceConflict` ends the transaction with a rollback, which the model treats as the transaction not having happened.
- Keys do not affect each other. Every statement of `claim`, `heartbeat`, `assertFence`, `cancel`, `put` and `delete` names one `(tenant, kind, id)`.

## Left out

- What a worker does between transactions: provider calls, browser work. The store cannot fence those. Rule 1 is about what commits in the store.
- What `encryptedBackup` and `restoreEncryptedBackup` (`index.ts:573-709`) do to records and retired revisions (tested in `tests/persistence-revision-restore.test.ts`, not modelled). The model has their claim rows and the lease base only, for rule 7, and one backup of the first store, restored at most twice; a backup of a restored store is tested (`tests/persistence-lease-epochs.test.ts`), not modelled. A restore whose epoch would pass `maxLeaseEpoch` (2^31 - 1, in 2093) is refused (`index.ts:679`). A key claimed and cancelled 2^22 times in one store is refused further claims (`LeaseGenerationsExhausted`, `:417-426`) until the store is backed up and restored; the bounds never reach that.
- Deadlocks between row locks, lock and connection timeouts, the 5 second SQLite busy retry (`index.ts:487-501`), pool failures.
- A claim's INSERT that waits on another transaction's uncommitted INSERT of the same key, which then rolls back: PostgreSQL computes the INSERT's row, and with it `${clock}+$5`, before that wait, so the lease can run from before the wait. The model's claim is one step at the clock of that step.
- Sealing and key rotation as cryptography (`persistence/sealing.ts`), key validation, list paging, transactions that touch several keys.
- Whether a lease is ever free again, and any other "eventually". The rules say only what never happens.
- A clock that steps backwards.
- More processes, ticks, changes of hands or writes than the bounds above.
- The callers. `verification/commands` is a separate model of the command path, which uses this lease.

## The chart

`chart.mmd` is the lease as a statechart, drawn by the `/statechart` skill from `Chart.cfg` with `view.mjs`. It is the small model: two processes, one clock tick, no record writes, no restarts, no writers without a lease. It does not draw steps that stay inside one state: starting a claim, a refused claim, reading the record, time passing without a lease running out, and whatever a newer lease does while an old holder is still at work.
